# Feature Specification: Manifest Schema Validation

**Feature Branch**: `008-manifest-schema-validation`
**Created**: 2026-10-28
**Status**: Draft
**Input**: "We must say and validate the JSON schema of the manifest, which seems to be https://developer.microsoft.com/en-us/json-schemas/teams/v1.24/MicrosoftTeams.schema.json. Think of something nice."

## Context

The tool reads the manifest, checks the icons and the lengths of a few fields and lets the user edit them. It never says whether the
manifest as a whole follows the schema that Microsoft publishes, which is what Teams and the admin centre validate on upload (a
manifest with an unknown property or a wrong type is refused with a message that names no field). This feature validates the manifest
against the official JSON schema of its own `manifestVersion` and explains every problem in plain words.

## Verified facts (read by hand on 2026-10-28)

- The schema URL pattern is `https://developer.microsoft.com/en-us/json-schemas/teams/vX.Y/MicrosoftTeams.schema.json`.
- Schemas exist for **1.10 to 1.17 and 1.19 to 1.30**. **1.18 does not exist** (HTTP 404), nor do 1.31 and 1.32 at the date above.
- They are JSON Schema **draft-04** documents that also use `const` and `if/then`. The keywords in use are: `type` (also a list),
  `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`, `pattern`, `format` (only `uri`), `minLength`, `maxLength`,
  `minimum`, `maximum`, `minItems`, `maxItems`, `uniqueItems`, `minProperties`, `oneOf`, `anyOf`, `not`, `if`, `then`, `dependencies`,
  `$ref` (into `#/definitions` or `#/properties/...`), `definitions`, `description`, `default`.
- The URL the user quoted (v1.24) is a real schema; the version of a package is the one in its own `manifestVersion`, not a fixed one.

## Decisions

- **No network (Principle II).** The schemas are downloaded **once, by a developer script**, never by the tool. They are bundled in the
  tool as data (`src/schemas/`), generated by `scripts/gen-schemas.mjs` from the downloaded files, with the date and the URL of each.
  No dynamic import and no new runtime dependency: the validator is the tool's own code (about 250 lines) for the keywords above.
- **The oracle is an independent validator.** The tests compare the tool's verdict and the places it blames with `ajv` (a development
  dependency only) on a matrix of mutated manifests over every bundled schema.
- **A schema that uses a keyword the validator does not know** makes a test fail, so a new schema version cannot be bundled silently.
- **The check never blocks saving.** Problems are a `warning`, not a `fail`: the tool cannot edit most fields, and a package that was
  already invalid when opened must still be saveable after a fix of something else. The user sees every problem and decides.
- **Descriptions are shortened** to their first sentence (at most 160 characters) in the bundle, to keep the tool small.

## User Scenarios & Testing

### User Story 1 - Is my manifest valid? (P1)
In the Checks step a card **Manifest schema** says either "The manifest follows schema v1.19" with how many entries were checked, or
"N problems against schema v1.19". It names the schema (version and URL, with a Copy button) and says what it does not prove.
**Tests**: a valid package shows the success state with the version, the URL and a count of checked entries; an invalid one shows the
count.

### User Story 2 - Every problem is explained (P1)
Each problem is a row with the **path** (`developer.websiteUrl`), the **problem in plain English**, what was **expected**, what was
**found**, the **description** the schema gives for that entry, and, for an unknown property, a **"Did you mean"** when a known one is
close. Problems are grouped by the top-level entry (`developer`, `icons`, `bots`...) with a count.
**Tests**: one case per keyword with the exact message; the suggestion appears for a near miss and not for a far one.

### User Story 3 - It follows my edits (P1)
The validation runs on the manifest as it will be saved, so an edit that fixes or breaks a field changes the card at once, and the
original manifest and the new one are validated against the same schema.
**Tests**: editing a field changes the result; the result is for `shown.text`, not for the original.

### User Story 4 - Versions (P2)
The schema is chosen from `manifestVersion`. A version with no schema (1.18, 1.31, `"abc"`, a number) is not validated and the card says
so, naming the versions that are bundled. A missing `manifestVersion` is validated against the newest bundled schema, with a note. If
`$schema` names another version than `manifestVersion`, a note says so.
**Tests**: each bundled version validates a valid manifest of that version; the unsupported cases; the notes.

### User Story 5 - In the report (P2)
The checks report holds a `schema` section (version, state, problems). The check list has one row `schema.valid`.
**Tests**: report content; the check id has a fix text.

### User Story 6 - Not JSON (P3)
A manifest that is not JSON is already refused by the reader; the card is not shown.

## The validator (what "validate" means)

Draft-04 semantics for the keywords listed, with these choices:
- `type` accepts a list; `integer` is a number with no fraction; `null` is its own type.
- `required` and `properties` apply to objects only; a keyword about a type that the value does not have is ignored (as in the draft).
- `additionalProperties: false` rejects every key not in `properties`; keys starting with `x-` are not special (the Teams schema does not allow them).
- `oneOf`: exactly one branch must match. `anyOf`: at least one. `not`: the branch must not match. `if/then`: `then` applies when `if` matches.
- `dependencies`: if the key is present, either the listed keys are required (list form) or the value must also match the schema given (schema form, which the Teams schemas use in 13 places).
- `format: "uri"`: the text must start with a scheme (`name:`) followed by something; the check is deliberately loose, like most validators.
- `pattern` is a JavaScript regular expression (as in the schemas), unanchored.
- `$ref` is a local pointer (`#/definitions/NAME`, or a path such as `#/properties/bots/items`); any other form, or a pointer that leads nowhere, is reported as an unsupported schema, never ignored.
- When a `oneOf`/`anyOf` fails, the problems of the branch that is closest (the one with the fewest problems; the one whose `type` equals the value's type first) are shown, and when no branch has the right type one problem lists the types allowed.
- A problem is blamed on the **deepest** path it can name, in dotted form (`bots[0].scopes[1]`); the keyword and the schema entry are kept.

## Requirements

- **FR-001** `scripts/gen-schemas.mjs` turns the downloaded schemas into `src/schemas/teams-vX.Y.json` (one per version, minified, descriptions shortened, with the source URL and the date of reading), and `src/schemas/index.ts` lists them.
- **FR-002** `services/schema/validate.ts` implements the keywords above and exposes `validate(data, schema)` returning problems; it reports an unsupported keyword or `$ref` form as an error of the schema, not silently.
- **FR-003** `services/schema/index.ts` exposes `validateManifestText(text)` returning `{ state, version, url, problems, checked, notes, bundled }` with `state` one of `valid`, `invalid`, `no-schema`.
- **FR-004** Problems carry `path`, `keyword`, `message`, `expected`, `found`, `description`, `suggestion`; messages are the plain-English forms in `contracts/ui-contract.md`.
- **FR-005** `runChecks` adds one check `schema.valid` (verdict `pass` or `warning`, never `fail`) when the manifest text is given; `fixes.ts` has an answer for it.
- **FR-006** The Checks step has a card `#schema` (before the automatic checks) with the summary, the schema name and Copy, the notes, and the problems grouped by top-level entry.
- **FR-007** The card and the check are computed from the manifest as it will be saved.
- **FR-008** The checks report holds a `schema` section.
- **FR-009** No network call, no dynamic import, no runtime dependency (Principle II); colours from CSS custom properties; both themes; no emoji.
- **FR-010** A test fails when a bundled schema uses a keyword the validator does not implement.
- **FR-011** `ajv` and `ajv-formats` are development dependencies only and appear nowhere under `src/`.

## Success Criteria

- SC-001 Every FR has a test in the traceability table of `tasks.md`; the matrix runs every bundled schema.
- SC-002 For every bundled schema and every mutation of the matrix, the tool and `ajv` agree on valid or invalid, and on the set of paths and keywords blamed (leaf problems).
- SC-003 `npm run test:mutation` kills the mutants of `validate.ts`, `index.ts` and the changed lines of the views.
- SC-004 Not covered: whether Teams accepts the package (it validates more than the schema: icons, domains, store rules), and the look of the card in PPTB in both themes (manual).
